# BodyRes — Звіт про деплой: Synology NAS і Hostinger

## Коротко: що саме розгорнуто

- **Synology NAS**: локальний preview-сервер у Docker на `http://nlmhelp.keenetic.link:18084/` (NAT → NAS `10.0.1.12:8080`, контейнер `bodyres-web-1`, образ `bodyres-web:latest`).
- **Hostinger production**: статичний сайт на `body-re.store` з файлам у `public_html` через FTP.
- **Основне обмеження**: після заливки файлів Hostinger продовжує віддавати стару сторінку через LiteSpeed edge cache; файли на сервері оновлені, але публічно ще показується старий кеш.

---

## 1) Деплой на Synology NAS (preview)

### Що було зроблено
1. **Підтягнено код** на NAS через Git (repo: `BodyRes`).
2. **Зібрано Docker-образ** через SSH:
   - Dockerfile у репозиторії (Node/Next.js), потім `docker build`.
3. **Піднято контейнер**:
   - `docker-compose` (або `docker run` у відповідному ланцюжку команд) для `bodyres-web-1`.
4. **Перевірено локальний preview**:
   - локально через `curl` на `10.0.1.12:8080` (тіло сторінки 200 OK, `8413` байт),
   - зовні через Keenetic NAT `http://nlmhelp.keenetic.link:18084/`.

### Які інструменти використано
- **DSM API** для логіну/перевірки доступу.
- **SSH через paramiko**:
  - підключення `vaoferi@10.0.1.12:22`, команди з `sudo -S` + пароль (не друкуємо),
  - перегляд стану Docker і запуск образу.
- **curl** для HTTP-перевірки відповіді.

### Що зафіксовано як важливе
- Превʼю на NAS працює, **контент новий** після перезбірки образу і рестарту контейнера.
- NAT на Keenetic повʼязує зовнішній порт `18084` з NAS `8080`.

## 2) Деплой на Hostinger (production)

### Що було зроблено
1. **Зібрано статичний out/** локально:
   - `npm run build:static` (через `scripts/build-static.mjs`).
2. **Завантажено файли на Hostinger FTP**:
   - протокол: FTP,
   - хост: `45.84.204.93`, порт `21`,
   - користувач: `u716984629` (пароль у файлах середовища, не публікується),
   - remote-каталог: `public_html`,
   - метод завантаження: Python `ftplib` скрипт у кілька потоків,
   - результат: **230 файлів завантажено, 0 помилок**.
3. **Перевірено FTP-вміст**:
   - побайтово звірено ключові файли `public_html/index.html`, `sharp-template/Sharp/index.html`, CSS і відео — на сервері вони **оновлені**.

### Які інструменти використано
- **Python `ftplib`** скрипт `Temp\ftp_upload.py` (рекурсивний `STOR`).
- **curl/urllib/Playwright** для продових перевірок.
- **Playwright `check_prod_page.js`** для браузерної верифікації DOM і контенту.

### Ключові перевірки (що довели)
- FTP-перевірка: файли нові → **OK**.
- HTTP-перевірка `https://body-re.store/`: **200**, але iframe версія й далі показує стару (`v=20260804-2`).
- HTTP-перевірка шаблону `https://body-re.store/sharp-template/Sharp/index.html`: **новий**, `has 68/1: True` і т.д.
- Реальне завантаження у браузері (Playwright): стара версія root-сторінки через кеш, далі поки не оновлюється.

### Додатково: фікс .htaccess для no-cache (FTP)
- Створено файл `public_html/.htaccess` з LiteSpeed/Apache no-store директивами для HTML.
- Це покращило оновлення шаблону, але **edge-кеш index.html все одно залишився старим** до явного очищення кешу в Hostinger або TTL/нульової політики з боку edge.

## 3) Що саме зараз не так на проді

- **Файли з БД/тегів у памʼяті вже нові**, але **LiteSpeed edge cache** тримає стару копію:
  - `iframe v=20260804-2` у HTML,
  - `has cache-bust comment: False` на root-сторінці,
  - маркер `68/1` на `/` поки `False`, але на `/sharp-template/Sharp/index.html` вже `True`.

Отже:
- **FTP-деплой успішний**,
- **кеш Hostinger ще не скинутий**.

## 4) Що треба зробити руками у hPanel (критично)

1. Увійти в Hostinger `hPanel`.
2. Перейти в **Websites → body-re.store → Cache**.
3. Натиснути **Clear cache / Purge all** (якщо є — також CDN/Cloudflare purge).
4. Після цього оновити браузер `https://body-re.store/`.

**Чому саме руки:** на цьому тарифі/хості дійсно радикальний спосіб скидання edge-кешу доступний тільки через UI керування (кнопка в hPanel), а не через FTP.
