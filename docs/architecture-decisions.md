# Архітектурні рішення BodyRes

## Next.js: тільки `STATIC EXPORT`

### Контекст
Проєкт може працювати у двох режимах:

1. `STATIC EXPORT` - готові HTML/CSS/JS файли без окремого Node.js сервера.
2. `SERVER / SSR / API` - потрібен Node.js сервер або Docker, що підвищує вартість і складність розгортання.

### Що вирішили
Для BodyRes використовуємо тільки `STATIC EXPORT` як цільовий режим розгортання.

### Чому так
- Це дешевше для хостингу.
- Це простіше для підтримки.
- Для поточного сайту не потрібні SSR або API-ендпоїнти.
- Основний контент уже живе в статичному шаблоні, тож статична збірка відповідає реальній архітектурі проєкту.

### Що не можна ламати
- Не переводити проєкт на SSR/API без окремого рішення.
- Не прив’язуватися до обов’язкового Node.js runtime для публічного хостингу.
- Не ускладнювати деплой там, де достатньо статичних файлів.

### Пов’язані файли
- `README.md`
- `DEPLOY_INSTRUCTIONS.md`
- `next.config.ts`

## Публікація службових файлів та сповіщення індексаторів

### Контекст

Hostinger production віддає лише вміст `out/`. Створення `robots.txt` або `sitemap.xml` у source tree до build не гарантує, що ці файли відповідають саме опублікованим HTML-сторінкам. Сповіщення до завершення FTP upload може повідомити про URL, яких ще немає в production.

### Що вирішили

Після static build аналізуємо HTML з `out/`, порівнюємо його з попереднім production manifest і пишемо службові файли також у `out/`. FTP deploy з `--notify` очікує відповідний `buildId` у production manifest, а потім повідомляє лише додані та змінені live URL.

Для static export каталог `.../index.html` у sitemap, feed, `llms.txt` і manifest завжди представляємо як URL зі слешем наприкінці: `.../`. Це збігається з `trailingSlash` у Next.js та canonical metadata сторінки.

На канонічних статичних сторінках використовуємо звичайні HTML-посилання, а не `next/link`. Інакше Next.js 16 може виконувати RSC-prefetch за шляхом, який звичайний Hostinger static hosting не зіставляє з експортованим файлом, і користувач бачитиме 404 у консолі під час навігації.

Якщо production явно повертає `404` для manifest, попередній локальний стан скидається: це перший відстежуваний реліз, тому коренева сторінка має бути подана до IndexNow, а не помилково вважатися незміненою.

### Чому так

- `lastmod` не оновлюється фальшиво для сторінок без зміни контенту.
- IndexNow не отримує видалений URL як нібито доступний.
- Production state перевіряється до зовнішніх повідомлень.
- Сайт лишається повністю статичним.

### Що не можна ламати

- Не запускати notifier до FTP deploy і live manifest check.
- Не зберігати Google/Telegram/FTP secrets у репозиторії.
- Не замінювати sitemap Google Indexing API для звичайних сторінок.
- Не включати `/sharp-template/Sharp` у sitemap, feed, `llms.txt` або manifest: це внутрішній iframe шаблону головної, а не окрема публічна сторінка.
